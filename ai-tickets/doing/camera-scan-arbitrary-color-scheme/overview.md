# 티켓: 제조사 배색과 무관한 실물 큐브 스캔

> 상태: **진행 중**. 4개 phase. 착수 전 설계 결정 3건 확정 완료(아래 "확정된 설계 결정").
> 최대 리스크는 Phase 2(유사색 임계값)와 Phase 4(실물 큐브 조달)에 있다.

## 진행 상태

| Phase | 상태 | 비고 |
| --- | --- | --- |
| 1 | 구현 완료 · 실기기 확인 대기 | `scan-orientation.js` 신규, 슬롯 순서 `[0,2,3,1,5,4]`, 테스트 35개 |
| 2 | 구현 완료 · 실측 fixture 미확보 | `palette`/`separation`/`warnings` 추가, `centerMap` 제거. 임계값은 잠정 |
| 3 | 구현 완료 · 실기기 UI 확인 대기 | `activeFaceColors` 분리, 면 단위 재촬영, 경고 배너 |
| 4 | 차단됨 | **비표준 배색 실물 큐브 조달 필요.** 코드 작업으로 대체 불가 |

Phase 1~3 은 코드가 끝났고 Jest 199개가 통과한다. 남은 것은 전부 실기기·실물 큐브가
있어야 하는 작업이며 Phase 4에 모여 있다.

## 목적과 배경

현재 카메라 스캔의 색 분류기는 6개 센터를 앵커로 사용하는 상대 분류 방식이지만, 사용자
경험에는 기본 배색 가정이 남아 있다.

- 촬영 안내가 흰색=U, 빨강=R, 초록=F, 노랑=D, 주황=L, 파랑=B를 전제로 한다.
- 검토 화면과 수동 수정 팔레트가 `FACE_COLORS` 고정 색을 사용한다.
- 스캔 상태를 3D 큐브에 적용하면 실제 제조사 색이 아니라 앱 기본색으로 표시된다.
- `centerMap`은 실질적인 촬영 팔레트가 아니라 고정 면 인덱스만 반환한다.

제조사에 따라 보라색·분홍색·청록색 등이 사용되거나 기본 배색의 인접/반대 관계가 다를 수
있다. 사용자가 임의의 첫 면을 기준으로 선택하고, 색 이름이 아닌 물리적 회전 안내에 따라
6면을 촬영하면 앱이 센터 RGB를 세션 팔레트로 만들고 내부적으로만 U/R/F/D/L/B 인덱스로
정규화해야 한다.

## 핵심 원칙

- 솔버와 `validateFacelets()`에는 지금처럼 정규화된 `0~5` facelet만 전달한다.
- 실제 색상과 내부 면 인덱스를 분리한다.
- 촬영 면의 관계와 방향은 색 이름이 아니라 사용자의 큐브 회전으로 확정한다.
- 스캔 검토와 스캔 Solve 중에는 실제 센터 팔레트를 표시한다.
- 셔플·리셋으로 일반 모드에 복귀하면 기본 `FACE_COLORS`를 복원한다.
- 서로 카메라상 구별되지 않는 색 조합은 조용히 통과시키지 않고 사용자에게 경고한다.

## 확정된 설계 결정

착수 전 분석에서 미결정으로 남아 있던 3가지를 아래로 확정한다. 각 phase는 이 결정을 전제로 한다.

### 결정 1 — 방향 규약은 유지하고 촬영 순서만 바꾼다

`camera-cube-scan` 티켓의 방향 규약(면별 "화면 위쪽에 오는 면")은 **그대로 둔다**. 이 규약이
`FACE_DEFS.slots`의 row-major 순서와 묶여 있어, 바꾸면 면마다 9칸 순열이 추가로 필요해진다.

대신 촬영 **순서**를 바꾼다. 규약의 6개 자세를 노드로, 단일 90° 회전(pitch/yaw)을 간선으로
놓으면 인접 관계는 다음과 같다.

```
U^B  ── pitch ──  F^U  ── pitch ──  D^F
                   │
              yaw  ├── R^U ── yaw ── B^U ── yaw ── L^U
                   └── L^U (반대 방향 yaw)
```

`U^B`와 `D^F`는 둘 다 `F^U` 하나에만 붙은 **차수 1 노드**다. 해밀턴 경로의 끝점은 최대 2개인데
두 리프가 같은 노드에 매달려 있으므로 **6면을 단일 90° 회전만으로 한 번씩 도는 경로는 존재하지
않는다.** 복합(2회) 회전이 최소 1회 필요하다.

현재 순서 `U → R → F → D → L → B`는 복합 전이가 **2회**(`U→R`, `D→L`)로 최적이 아니다.
아래 순서로 바꾸면 복합 전이가 **1회**, 총 물리 회전 6회로 최소가 된다.

| 스텝 | 조작 | 촬영 슬롯 | 화면 위쪽 |
| --- | --- | --- | --- |
| 1 | 기준면을 정면에 두고 위 방향을 정한다 | U (index 0) | B |
| 2 | 위쪽을 뒤로 넘겨 한 칸 굴리기 | F (index 2) | U |
| 3 | 같은 방향으로 한 칸 더 굴리기 | D (index 3) | F |
| 4 | 한 칸 되돌린 뒤, 오른쪽 면이 정면으로 오게 돌리기 | R (index 1) | U |
| 5 | 같은 방향으로 한 번 더 | B (index 5) | U |
| 6 | 같은 방향으로 한 번 더 | L (index 4) | U |

스텝 4만 복합이고, 그 앞 절반이 "직전 동작 되돌리기"라 애니메이션으로 안내하기 쉽다.

### 결정 2 — 정규화 순열은 필요 없다. `centerMap`을 제거한다

사용자가 고른 기준면을 **정의상 내부 U**로 삼는다. 물리 회전이 나머지 5면의 공간 관계와
방향을 확정하므로, 결정 1의 표에 있는 슬롯 인덱스를 `captureFace(slot)`에 그대로 넘기면
`scanFaceSamples`는 처음부터 내부 면 순서로 채워진다. 별도의 순열 코드가 없다.

따라서:

- `classifyFacelets()`에서 `centerMap`을 **제거한다**. 항등 배열을 반환하느니 없는 편이 낫다.
- `scan-orientation.js`는 데이터를 순열하는 모듈이 **아니라**, 회전 안내를 생성하고 그 결과가
  규약과 일치하는지 검증하는 순수 모델이다.
- `scan-ui.js`에서 "가이드 스텝 인덱스"와 "면 슬롯 인덱스"를 분리해야 한다. 현재는
  `currentScanFace` 하나가 두 역할을 겸하고 있다.
- 큐브 배색의 카이랄리티(BOY / 비BOY)는 물리 회전에서 자동으로 보존되므로 별도 처리가 없다.

### 결정 3 — `camera-cube-scan` Phase 8의 실측을 이 티켓 Phase 4로 흡수한다

`camera-cube-scan` Phase 8은 조명·재질 매트릭스 실측과 릴리스 게이트를 정의하지만 아직
실측 전이다. 이 티켓 Phase 3이 검토 화면과 3D 렌더링을 바꾸므로 **지금 Phase 8을 측정하면
Phase 3 완료 시점에 UI 검증 결과가 무효화된다.** 두 티켓의 매트릭스(조명 4종 × 재질 3종)와
릴리스 게이트(90%)도 사실상 같다.

- `camera-cube-scan` Phase 8은 **코드 하드닝·실패 복구 경로**까지만 책임진다.
- **실측 매트릭스와 릴리스 게이트는 이 티켓 Phase 4가 단독으로 소유한다.** 표준 배색은
  비표준 배색과 같은 회차에 baseline으로 함께 측정한다.
- 실기기 측정을 두 번 하지 않는다.

## 선행 조건 (코드 작업으로 대체 불가)

Phase 2의 실측 fixture와 Phase 4 전체는 **비표준 배색 실물 큐브 조달**이 선행 조건이다.

- `tests/fixtures/` 디렉터리는 아직 존재하지 않고, `camera-cube-scan` Phase 4도 합성 RGB
  테스트만 있는 "실측 대기" 상태다.
- 보라·분홍·청록 중 최소 1종, 가능하면 3종의 실물 큐브가 없으면 Phase 2는 합성 fixture까지만
  완료할 수 있고 Phase 4는 착수 자체가 불가능하다.
- 큐브를 구하지 못하면 Phase 1~3까지 구현한 뒤 **기능을 숨긴 채** 두고, Phase 4를 별도
  티켓으로 분리하는 편이 낫다.

## 전체 수용 기준

- 흰·빨·초·노·주·파가 아닌 6색 큐브도 색 이름을 알 필요 없이 6면 촬영 가능
- 임의로 선택한 첫 면을 기준으로 촬영해도 정규화된 facelets가 유효하고 실제 상태와 일치
- 검토 화면의 전개도와 수동 수정 팔레트가 촬영한 센터 색을 사용
- 스캔한 상태의 3D 큐브가 실제 팔레트를 사용하고 셔플·리셋 시 기본 팔레트로 복원
- 센터 두 색의 구분도가 지나치게 낮으면 촬영 결과를 조용히 확정하지 않고 경고
- 기본 배색 큐브의 기존 스캔 동작에 회귀 없음 — 특히 **표준 배색에서 유사색 경고가 뜨지 않을 것**
  (기본 `FACE_COLORS`의 최소 쌍거리는 빨/주 ΔE 31.8이므로 임계값이 이보다 낮아야 한다)
- 정확도 게이트는 팔레트 난이도에 따라 분리한다 — Phase 4 참조
- `npm test`, Android 빌드·린트 통과

## 비스코프

- 투명·거울·금속 재질 큐브의 완전 자동 인식 보장
- 서로 카메라상 사실상 동일한 두 색의 자동 구분
- 2x2, 4x4 등 센터 구조가 다른 퍼즐
- 사용자가 임의 순서로 촬영한 뒤 영상만으로 면의 공간 관계를 추론하는 기능
