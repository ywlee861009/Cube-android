# Phase 6 — 인식 결과 확인·수동 수정 UI

> 상태: **미착수**
> 선행: Phase 4 (분류 결과·확신도), Phase 5 (스캔 플로우)
> 검증 주체: 실기기 수동 확인

## 문제/목표

색 인식은 반드시 틀린다. 문제는 **오인식이 조용하다는 것** — 사용자는 "앱이 이상한 답을
준다"고 느끼지 원인이 카메라라고 생각하지 않는다. 6면 전개도를 보여주고 직접 고칠 수 있게
한다. **이 UI는 있으면 좋은 게 아니라 기능 성립의 전제다.**

## 수정 대상

- `app/src/main/assets/cube.html` — 확인 오버레이 DOM
- 신규 `app/src/main/assets/js/scan/scan-review.js`
- 스타일 추가
- `app/src/main/assets/js/CLAUDE.md` — 모듈 표 갱신

## 구현 방향

### 화면

6면 전개도(십자 전개, 54칸)를 보여준다. 각 칸은 `FACE_COLORS`(`constants.js:2`)로 칠한다.
카메라 프리뷰는 이 시점에 끄고(`stopScan()`) 일반 화면으로 돌아온다 — 프리뷰를 켜둔 채
전개도를 겹치면 가독성이 나쁘고 배터리만 쓴다.

### 확신도 강조

Phase 4의 `confidence`가 낮은 칸에 시각적 표시(테두리·물음표 아이콘)를 준다.
**낮은 확신도 칸을 위로 끌어올리는 요약 배지**("확인이 필요한 칸 3개")를 두면
사용자가 54칸을 전부 훑지 않아도 된다. 실사용 만족도가 여기서 갈린다.

Phase 4의 자동 백트래킹이 개입한 칸이 있으면 별도로 표시한다 — 검증은 통과했지만
실물과 다를 수 있는 칸이다.

### 수정 인터랙션

- 칸 탭 → 6색 팔레트에서 선택 (센터 6칸은 수정 불가 — 색 정의의 기준점)
- 수정할 때마다 `validateFacelets()`(Phase 3) 재실행
- 검증 결과를 실시간 표시:
  - 색 개수 불일치 → "빨강 10개, 주황 8개 — 하나가 잘못됐어요"
  - 조각/패리티 위반 → `badIndices`의 칸을 하이라이트
- 검증 통과 전까지 "Solve 시작" 버튼 비활성

### 이탈 경로

- "다시 스캔" → Phase 5로 되돌아감 (샘플 폐기)
- "취소" → 기존 큐브 화면으로 복귀, 상태 변경 없음
- "Solve 시작" → Phase 7의 주입 경로

## 구현 시 주의

- 54칸 전개도는 세로 화면에서 작다. **탭 타겟이 최소 44dp 상당은 되어야** 한다.
  칸이 너무 작으면 확대 뷰나 면 단위 편집으로 전환하는 편이 낫다
- 수정 중 `validateFacelets()`를 매 탭마다 호출해도 54칸 검사는 즉시 끝나므로 성능 문제 없음
- 다크모드에서 `#FFFFFF`(U면) 칸이 배경과 붙지 않도록 테두리 필요
- 색약 사용자를 위해 각 칸에 색 이니셜(U/R/F/D/L/B)을 옵션으로 표시하는 것을 검토.
  `backlog/platform-accessibility.md`와 중복되는지 확인할 것

## 검증

- 완성 큐브 스캔 → 전개도가 6면 단색으로 나옴
- 의도적으로 한 칸을 가린 채 스캔 → 해당 칸이 낮은 확신도로 표시됨
- 잘못된 칸을 수정 → 검증 통과 → Solve 버튼 활성화
- 검증 실패 상태에서 Solve 버튼이 눌리지 않음
- 색 개수를 일부러 어긋나게 만들었을 때 안내 메시지가 사람이 읽을 수 있는 문장인지
- "다시 스캔" / "취소" 각각 상태 오염 없이 복귀
- 다크/라이트 모드 가독성
